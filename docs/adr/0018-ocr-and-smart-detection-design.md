# Phase 8 design: copying text from the screen, and clips that know what they are

Phase 8 lets the user copy text from anything on screen, and lets the popup say what a clip is. This record holds the decisions behind it. Where PLAN.md said something else, it says so.

## Decisions

1. **The owner approved the plan and these choices (2026-11-05).** Capture with GDI, only the chosen region. One overlay per monitor. Only text is kept, never the pixels. Incognito copies to the clipboard but does not record. The shortcut is Win+Alt+O. A link is opened only from the right-click menu. The language is the one in the user's Windows profile, with no picker.
2. **The region maths is pure and lives in Core.** `RegionMath` turns the two ends of a drag into a rectangle cut at the monitor's edges, with sides of at least 8 and at most 10,000 pixels (the most the Windows recognizer reads), and a failure with a plain message otherwise. It finds the monitor a point is on (the right and bottom edges belong to the next monitor), clips a selection to a monitor and gives it from the monitor's own corner, and scales a line thickness for a monitor's scale. Everything is in device pixels on the virtual screen, so monitors left of or above the main one have negative corners and nothing converts between window units and pixels. The tests cover a monitor at 150% to the left, one at 125% above, and drags in every direction.
3. **One overlay per monitor, and a drag stays on the monitor where it starts.** A selection across monitors would need one picture of monitors with different scales, which no single window can draw correctly. The overlay is a layered Win32 window drawn with GDI, not a WinUI window: the user must read the text under it, WinUI here has no see-through backdrop and acrylic blurs what is behind it. The pixels are premultiplied alpha, black at about 40 percent, the chosen area almost clear (alpha 1, so the mouse still reaches the window; a layered window passes the mouse through pixels with no alpha at all) and a border just outside it. The drawing is a pure function over a buffer and is tested without a screen. The overlay closes on the mouse button going up, on Esc, on a right click and when its token is cancelled. It takes the keyboard when it opens so Esc works.
4. **The overlay is always hidden from screen capture,** whatever the user's screen-capture setting or `--allow-screen-capture` say, so it can never be in the pixels that are read.
5. **Capture reads only the chosen rectangle.** GDI `BitBlt` from the screen into a bitmap the size of the region (never the whole screen, never another window's contents by handle), converted to blue, green, red, alpha with alpha set opaque, because the recognizer reads alpha 0 as see-through. The pixels live in a `ScreenImage` that zeroes its buffer when it is let go of, in a `finally`, so a failure or a cancel also clears it. Nothing is written to disk. Windows' own recognizer copies the pixels into buffers of its own (`CryptographicBuffer`, `SoftwareBitmap`) that ClipBench cannot zero; this is stated in the threat model.
6. **Recognition is Windows' own.** `Windows.Media.Ocr` with `OcrEngine.TryCreateFromUserProfileLanguages`, so ClipBench has no image parser of its own and no model. No language installed gives a message that names where to add one (Settings, Time and language, Language and region, Language options, Text recognition). A picture larger than the engine's limit, and any other failure, give a plain message that names nothing from the picture. Lines are joined with a line break. Chinese and Japanese text comes out with spaces between characters, as Windows returns it.
7. **What happens to the text.** It is trimmed. None found says so and changes nothing. Over the 2 MiB text limit it is refused. It is put on the clipboard first (the writer marks it as ClipBench's own write, so the listener does not record it a second time). Unless incognito is on it is then added to the history like any copy, as source "Screen text", so a secret is hidden and expires and it counts toward the history limits; with incognito on it stays on the clipboard only, and the notice says so. The notice says how many characters were copied, never which. The log holds the count and size, or an error code. Only one request runs at a time and a second shortcut press is ignored.
8. **Pinning keeps the text, not the picture.** PLAN.md said the image is never saved "unless the user pins the result". The owner chose to keep text only: the pixels are never stored, so there is nothing to pin. This is a deviation from the plan, recorded here.
9. **Detection is whole-text and ordered.** `ContentDetector` says what a clip is only when the whole trimmed text is exactly one thing: a color (hex of 3, 4, 6 or 8 digits, `rgb()`, `rgba()`, `hsl()`, `hsla()`, with commas or spaces, percent or fraction alpha), a link, an email address, a phone number, or code. The first match wins in that order. A sentence that contains a link is not a link. The parsers for colors, links, emails and phone numbers are hand-written with length caps, so they cannot take long. A phone number needs 7 to 15 digits and a leading plus or a separator, and is not a date or an IP address.
10. **Links are read, never fetched.** Only `http`, `https` and `www.` addresses count, written out in full, with the scheme and host in lower case. `javascript:`, `file:`, `data:`, `mailto:` and network share paths never count, and an address with embedded credentials (`https://user@host`, which can be used to disguise the real host) is refused. The popup row says "Link"; the right-click menu offers "Open the link in your browser", and only then is the address handed to Windows, which opens the user's browser. ClipBench itself makes no connection. This is the second place the app hands an address to Windows (the first is About), and Phase 9's network test must expect both.
11. **Code is a guess.** It adds up weighted signals (a keyword with its punctuation, a header line, a typical call) for C#, JavaScript, TypeScript, Python, Java, C and C++, Go, Rust, SQL, Shell, PowerShell and CSS, and names the language with the highest score when it reaches 3 (or 2 with several lines that end like code lines). HTML, XML and JSON are recognised by their shape, JSON by parsing it (at most 200,000 characters, 64 levels deep). Only the first 4,000 characters are scanned. Every pattern runs on the non-backtracking engine with a 250 ms limit, and text with none of the characters code is made of is skipped. It is a heuristic and is wrong in both directions; a test list of ordinary sentences guards against the common false alarms.
12. **The answer is computed once per clip and shown only when it is safe.** The library keeps it per clip, like the secret scan, and forgets it when the clip goes or everything is wiped. A secret that is hidden shows no swatch, no label and no link, because a link with a token in it would give itself away; revealing it shows them. A screen reader hears the kind ("link", "color #FF0000").
13. **The shortcut is Win+Alt+O,** editable in Settings like the other two and re-bound at once. The three shortcuts cannot clash: a clash falls back to the default, and when even the defaults collide with the choices all three return to their own. The tray menu has "Copy text from the screen".

## Considered options

- **Windows Graphics Capture.** Rejected: it needs Direct3D interop and a GPU surface for what GDI does in one call on a rectangle the user drew, and it would add code that sees more than the region.
- **One window across all monitors.** Rejected, see decision 3.
- **A frozen full-screen picture behind the overlay** (the way snipping tools work). Rejected: it reads the whole screen, which is what the plan says not to do.
- **A WinUI overlay.** Rejected, see decision 3.
- **A language picker.** Left out for now: the languages in the Windows profile are the ones the user has chosen to use, and Windows is where a recognition pack is added.
